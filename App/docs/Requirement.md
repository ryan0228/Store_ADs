# Shop Ads 圖片產生工具－需求規格

## 1. 目標

建立一套可在 Windows 獨立執行的圖片產生工具，從 `D:\CASE\Shop_ADs\yyyyMMdd-NN` 單一商品作業目錄讀取商品資料與原始圖片，使用可替換的雲端 AI 分析、選圖、排序、分組及產生繁體中文文案，再由本機確定性排版核心產生 1080×1080 社群圖片。

第一階段只負責輸入檢查、圖片生成、人工成品檢查與跨電腦封裝；Facebook 與 GitHub 發布屬於後續獨立階段。

## 2. 作業目錄

```text
D:\CASE\Shop_ADs\20260804-01\
├─ Product_Description.md
├─ Input\
│  ├─ 001.jpg
│  ├─ 002.png
│  └─ product.gif
├─ Work\
│  ├─ ai-plan.json
│  └─ preview.html
└─ Result\
   ├─ Generated\
   └─ Final\
```

作業名稱必須是有效日期加兩位數流水號，例如 `20260804-01` 至 `20260804-10`。每個作業只代表一個商品；圖片全部放入 `Input`，不再建立數字圖片群組。

工具必須提供 `new-job` 快速建立作業：預設使用本機當天日期，掃描 `01`～`10` 並建立第一個不存在的編號，複製正式商品說明範本，建立 `Input`、`Result\Generated` 與 `Result\Final`。不得覆蓋既有作業；當天已滿 10 個時拒絕建立。

## 3. 文字資料

### 3.1 Product_Description.md

必須包含以下 Markdown 標題：

- `商品名稱`
- `商品說明`
- `商品用途`（選填；留白時由 AI 根據名稱、說明與圖片推導）
- `參考資訊`（選填）
- `文案限制`（選填）
- `廠商文字說明`（選填）

這些內容提供整批商品資訊、後續 Skill 與發布文案使用。第一階段不強制將商品名稱畫在每張圖片上。

### 3.2 AI 生成計畫

使用者不再手動建立 `Img_Description.md`。AI 必須先產生結構化 `Work\ai-plan.json`，列出成品順序、來源圖片、受控版型、上標題、說明、下標題、未採用圖片及原因；使用者確認後才能合成。

AI 必須將商品描述、廠商文字與圖片內清楚可辨識的文字視為同一組參考資料，去除重複後整理功能、材質、操作、規格、尺寸與配件。若 `廠商文字說明` 有內容，必須辨識語言；日文翻譯為繁體中文，並固定產生最後一張摘要 PNG。沒有廠商文字時，只有達到設定的具體可驗證資訊門檻才產生摘要頁；資訊量少時不得為了湊頁數而產生。摘要以 `vendor_text` 版型固定置於最後，資訊過長時濃縮為適合 1080×1080 閱讀的重點，不得靜默截斷或加入來源未提供的宣稱。

## 4. 圖片處理

- 支援 `.jpg`、`.jpeg`、`.png`、`.webp`、`.gif`。
- 分析前以 SHA-256 過濾位元組完全相同的重複檔案，所有支援格式均適用；保留自然排序最前的一份，不刪除 Input 原檔，並在 Log 與 AI Plan 未採用清單記錄其餘檔案。
- AI 可為每張成品選擇一至四張靜態來源圖，並從 `hero`、`two_cards`、`three_cards`、`four_grid` 受控版型中選擇。
- AI 決定成品數量與順序，輸出連續命名為 `01.png`、`02.png` 等。
- 單影格 GIF 視為靜態圖片，可參與一至四張分組，最後輸出為帶品牌頁尾的 PNG。
- 多影格 GIF 視為動畫；每個動畫各自獨立、不合併、不加字、不重新編碼，可依計畫插入順序並命名為 `01.gif`、`02.gif` 等。
- 每個動畫 GIF 在本機擷取首、中、末三個代表影格並合成縮小預覽供 AI 判斷；不傳送完整 GIF，最終輸出仍維持原始位元組。
- 所有動畫 GIF 必須在 AI Plan 中恰好出現一次，不可被排除或當作靜態圖片。
- 手機照片須依 EXIF 修正方向。
- 靜態輸出統一轉為 sRGB PNG，尺寸固定為 1080×1080。
- 圖片採完整顯示，不裁掉商品主體。
- 預設使用 `clean` 版型，包含卡片、外框、陰影及小角度旋轉。
- 相同已確認計畫、輸入與設定重跑時，輸出排版必須一致。
- 每張 PNG 成品右下角必須顯示 `assets\branding\shop-footer.png` 品牌圖；該圖已包含「情趣時光」店名，不重複繪字。
- 多影格 GIF 依既定規則維持原始位元組，因此不加入品牌頁尾；單影格 GIF 輸出為 PNG 並加入品牌頁尾。

## 4.1 AI 邊界

- AI 不生成、重畫、換背景或改造商品圖片。
- AI 只能根據 `Product_Description.md` 與實際可見圖片內容撰寫繁體中文文案。
- 圖片內文字只能在清楚可辨識時作為資料來源；須與描述檔內容合併去重，無法辨識的字不得猜測。
- 不得杜撰尺寸、材質、價格、產地、功效或保證性宣稱。
- AI 可排除重複、模糊或低資訊圖片，但必須列出原因。
- 靜態圖片送出前建立移除 EXIF 且限制解析度的分析副本；原圖只供本機合成。

## 5. 輸出與覆蓋

- 程式生成檔案只寫入 `Result\Generated`。
- 重新生成群組前，只清理該群組在 Generated 中的舊輸出與舊分頁。
- 不得刪除或覆蓋 `Result\Final`。
- 人工確認或加工完成的圖片由使用者放入 `Result\Final`。
- 發布封裝預設只接受 Final，不得無提示地改用 Generated。

## 6. 設定

- 共用設定使用外部 TOML 檔，可調整尺寸、版型、色彩、字型、AI Provider、模型與分析限制。
- API key 可存於本機 `App\config.local.toml`；該檔必須被 Git 忽略，且不得進入 Log、Manifest、EXE 或封裝。
- AI Provider 採統一介面；OpenAI 與 Google 皆必須輸出相同的 AI Plan 契約，完成各自 Adapter 後可由設定切換。
- `ai.summary_min_facts` 設定沒有廠商文字時產生摘要頁的最低具體資訊數，預設為 3。
- AI API 遇到 429、500、502、503、504 暫時性錯誤時最多嘗試三次退避重試；其他錯誤立即停止。
- 日期目錄可用 `job.toml` 覆寫允許的視覺設定。
- 第一階段不保存 Facebook 或 GitHub 憑證。
- 後續憑證必須放在 Windows Credential Manager；一般設定檔只保存憑證名稱。

## 7. 防呆與追蹤

- 提供 `new-job`、`validate`、`analyze`、`generate`、`check-final`、`package`、`verify-package` 七個獨立命令。
- 錯誤訊息必須包含錯誤代碼、執行階段、檔案路徑與處理建議。
- 單一群組失敗不得阻止其他合法群組生成，但整體命令須回傳非零結束碼。
- 每次生成產生 `run-manifest.json` 及時間戳記 Log。
- Manifest 記錄輸入與輸出 SHA-256、程式版本、設定、群組結果及錯誤。
- Log 不得記錄 Token、密碼或其他機密。

## 8. 跨電腦封裝

- `package` 只封裝已通過檢查的 Final 圖片。
- 封裝檔包含商品／圖片 Markdown、Final 圖片及 `publish-manifest.json`。
- Manifest 記錄每個封裝檔案的 SHA-256。
- 封裝檔不得包含本機設定、Token、密碼或私鑰。

## 9. 驗收條件

1. 一至四張來源能依受控版型生成單張 PNG，多組計畫能依展示順序連續命名。
2. 多個動畫 GIF 均維持位元組內容不變，只依順序更名複製；單影格 GIF 能當作靜態圖合成。
3. 更換來源後重跑會覆蓋 Generated，且清除不再需要的舊分頁。
4. 重跑不改動 Final。
5. 缺少 Markdown、欄位、字型或圖片損壞時能指出明確環節。
6. 過長文字不會被靜默截斷；無法排入時該群組失敗。
7. 封裝前缺少 Final 時拒絕執行。
8. 封裝 Manifest 的 SHA-256 能驗證所有檔案。
9. 商品描述、廠商文字與圖片文字能去重彙整；資料達門檻時產生且只產生一張最後摘要頁，資料不足時省略。
